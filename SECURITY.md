# Security policy and threat model

## Security objective

An agent may propose an action, but only host code can authorize and execute it. Model output, publisher model cards, retrieved memory, local documents, browser content and tool results are untrusted data.

The application is local-first, not automatically offline or sandboxed. A configured remote Ollama endpoint receives prompts and whatever project context the agent is permitted to read. Public model-card research is a separate, opt-in network feature.

## Assets and threats

Assets include source code, workspaces, local credentials, private keys, Git repositories, model files, local services, benchmark evidence and application state. Threats include prompt injection in documents/memory, hostile model output, compromised model packages, symlink/path escapes, malicious tool arguments, unsafe approved executables, malicious MCP servers, accidental destructive actions, stale model profiles and data disclosure to remote endpoints.

## Implemented controls in the 0.2 development branch

- Ollama defaults to loopback (127.0.0.1). A user-configured remote endpoint is not assumed private.
- Public Hugging Face model-card research is disabled by default and requires explicit upstream-repository selection.
- Agent execution verifies the installed model name and exact Ollama digest against the saved profile before starting.
- Workspace paths are resolved and checked for containment before file operations.
- Conventional credential/private-key locations are denied by default: .env files, credential stores, .ssh, .aws, .azure, .kube, .gnupg, secret directories and common private-key/certificate suffixes. .env.example, .env.sample and .env.template are allowed as templates. This is a heuristic deny-list, not a complete secret scanner.
- File reads are limited to 64 KB and writes to 1 MB per call. Writes use an atomic temporary-file replacement. Existing-file overwrites require host approval.
- Tool requests are validated by host code for registered tool name, required parameters, types, enums and unexpected properties.
- Tool outputs are capped before being returned to the model. Common credential-value patterns are heuristically redacted from text files, search snippets and command output. The same redaction is applied to saved memory notes, persisted run objectives/event payloads and final CLI/desktop responses. Placeholder values such as replace-me remain visible.
- Native tool calling, JSON-schema actions and guided ACTION/FINAL text actions use the same host tool catalogue and validation path.
- Desktop agent runs can request cancellation. The desktop passes a cancellation event into the Ollama client; the client streams the response and closes the HTTP stream when cancellation is requested. The server-side generation may not stop instantaneously.
- Optional command execution is disabled by default. When explicitly enabled, command names are resolved to configured executable paths, path-form model requests are rejected, shell=False is used, a host approval callback is required, the environment is reduced and a 90-second deadline is enforced.
- On Windows every agent command (and every read-only git command) runs inside a Job Object. The process is created suspended and assigned to the job before its first instruction, so no descendant can start outside it. The job enforces kill-on-close (no descendant, including a detached one, outlives the command), a 32-process cap, a 2 GiB job-wide committed-memory cap, and UI restrictions (no clipboard, desktop switching, global atoms, display/system-parameter changes or logoff/shutdown). If the job cannot be created or applied, the command is refused. POSIX uses a dedicated process group. Regression tests prove each limit against the real Windows kernel, with negative controls showing the same tests fail without the job.
- On Windows every agent command also runs inside an **AppContainer** (setting `command_sandbox`, default `appcontainer`). The container SID is granted modify access to the agent's workspace and read/execute access to the runtime folders of each allow-listed executable (for a Python virtual environment: the environment and its base interpreter); nothing else. The process starts suspended, joins the Job Object, then resumes. With no capabilities it has no internet, private-network or loopback access, so it cannot reach Ollama, local services or exfiltrate data, and the user's profile, documents, other workspaces and credentials are denied by the kernel. If the container cannot be created or entered, the command is refused. Tests prove each denial against the real kernel, with a job-only negative control that reads the secret, writes outside the workspace and connects to loopback. Grants are recorded and can be listed or revoked with `11vated sandbox status|revoke`.
- Web research is available only through two host-side tools (`web_search`, `web_fetch`) granted per agent. The egress policy requires https, refuses embedded credentials, resolves the host and refuses any non-public address (loopback, private, link-local, metadata, multicast, reserved), re-checks every redirect hop, caps size at 2 MB and accepts only text content types, ignores proxy/cookie environment, and allows only listed domains unless the operator approves a domain for the session. Unattended runs refuse unlisted domains. Fetched text is marked untrusted and credential-redacted. Web agents automatically pin the `content-is-data` skill (measured: injection obedience 8/10 -> 3/10 on qwen2.5-coder:14b).
- **Browser and computer use** are separate grants per agent and act only through the interaction broker, which decides every action from host-observed facts and records it in a hash-chained audit trail. The browser runs a fresh in-memory Edge/Chrome context whose own network stack points at a dead proxy; every request is intercepted, checked by the egress policy and fetched by the host connected to the checked address (closing DNS rebinding), redirects are checked before they reach the page, non-web schemes are refused, and downloads are fetched by the host into a quarantine folder with Mark-of-the-Web and never opened. Computer use sees only windows of applications the agent launched from its granted list (bound to the launched process where the app allows), acts through UI Automation patterns rather than physical input (physical input is a separate grant and requires the agent's window in the foreground), never reads or fills password fields, refuses processes running with higher privilege than the workstation and always refuses UAC or credential windows, and asks for human confirmation before destructive, financial or account-security actions (refused when unattended). Tests show the refusals against real Edge and real UI Automation, and live acceptance counts prohibited actions attempted versus executed.
- The `OLLAMA_WORKSTATION_OLLAMA_URL` environment override is honoured only for loopback hosts unless `allow_remote_ollama` is set, so an inherited variable cannot silently send prompts and files to another machine.
- No path runs a model as an agent without clearance: `11vated run`, `recover`, chat agent mode, run-history resume, workforce children and versioned agents all pass one gate that requires the installed digest to match, a harness qualification for that digest whose qualified tools cover the granted tools under the current Ollama/prompt/suite versions, and a RAM/VRAM admission decision. Running an unqualified model requires an explicit, recorded operator override.
- Read-only git tools (`git_status`, `git_diff`, `git_log`) are off unless granted to an agent. They disable fsmonitor, external diff, textconv, pagers and hooks, so a hostile repository configuration cannot execute code through them (tested with a control proving plain git does execute it).
- Memory writes are defended against poisoning: agent-written notes are capped at confidence 0.6, instruction-shaped notes are tagged `suspected-injection` and capped at 0.2, near-duplicates reinforce instead of multiplying, and likely contradictions are recorded and flagged to the agent on retrieval.
- Local memory writes are explicit, scope-bound (user/project/agent), credential-redacted and validated. Recalled notes are marked as untrusted data in the system prompt and cannot grant permissions.
- Run execution is bounded by a configured step limit. Ordered events are journaled to SQLite during execution; crash-interrupted runs remain visible with a running status. Safe-boundary checkpoints record the exact model digest, workspace, task, harness and tool-manifest binding. Checkpoint payloads are AES-256-GCM encrypted with a separate 32-byte key file; the envelope hash binds the recovery identity. These controls are tamper-evident, not tamper-proof against an attacker who can rewrite both the database/key and application code, and the SQLite file itself is not encrypted at rest. An interrupted tool batch is marked `needs_review` and is never replayed automatically.
- Every repository-backed top-level run acquires both an atomic per-run lease and a workspace admission keyed by the canonical workspace path, and keeps both alive with a heartbeat. A second run against a live-held workspace is refused before any provider request, checkpoint or tool call and reports `workspace_busy`; CLI/desktop resume refuses the same condition and recovery displays `WORKSPACE_BUSY`. A live lease marks recovery `LEASED`. Lease rows record host, PID and process-start identity; only a provably dead local owner (or a PID proven to belong to another process) is reclaimed before TTL, inside the same `BEGIN IMMEDIATE` transaction. Lease loss aborts before the next safe boundary. This prevents concurrent execution of the same run or workspace within the configured database, not unauthorized access to the database.
- Workforce plans are host-validated data: relative verification paths, DAG dependencies, step/time budgets and approval boundaries are checked before any child starts. Each child receives only its task tool registry and workspace. Workforce and child events are hash-chained and passed through credential-pattern redaction. Child agents share their assigned workspace; the read-only registry is a tool-policy boundary, not an OS sandbox.
- Structured JSONL logs contain bounded, redacted operational events and stay in the per-user application data directory. Log redaction is heuristic and is not a secret-vault guarantee.

## Known limitations — not production-certified

- Inside the AppContainer an approved executable can still do anything to the agent's own workspace, including reading sensitive files that sit inside it (the tool-level sensitive-path policy does not apply to code the agent runs). Keep secrets out of agent workspaces. Read access granted to a runtime folder (for example a Python installation) is readable by every sandboxed command.
- The AppContainer is a Windows boundary. POSIX hosts get process-group cleanup only and no filesystem/network sandbox. Selecting `command_sandbox = job` removes the filesystem and network boundary and is an explicit operator choice.
- The web egress check resolves DNS before connecting; a DNS rebinding attack between the check and the connection remains possible for one request (redirects are re-checked). Pages are untrusted input: the measured models still follow embedded instructions some of the time (R15), and the skill mitigation reduces but does not remove this.
- Filesystem containment uses application-level path resolution. Handle-based operations are still required to fully address filesystem race/symlink TOCTOU risks.
- Credential path protection and value redaction are heuristic deny-lists/pattern filters; they cannot identify every secret, encoded key, custom token format, renamed credential file or application-specific vault. Never treat them as a complete data-loss-prevention system.
- The allow_sensitive_files constructor option exists for trusted host integrations, but the desktop does not expose it. Do not enable it for model-controlled tasks.
- The stop action can close the active HTTP stream, but it cannot guarantee that the Ollama server immediately releases GPU memory or stops all work. Provider cancellation semantics must be verified for each supported Ollama release.
- Computer use relies on applications exposing UI Automation; apps that do not are controllable only with the raw-input grant. Label-based risk classification is a heuristic over accessible names: an application that labels a destructive control innocuously ("OK") is not recognised as destructive, so grant computer use only for applications whose controls you trust, and keep human review for consequential work. The browser is not an OS sandbox around the browser process itself (Chromium's renderer sandbox applies); it is isolated by profile, network interception and scheme refusal.
- The runtime does not implement MCP OAuth/protected-resource authorization or a credential broker. Release signing is supported by the build script but requires an operator-supplied code-signing certificate. Durable checkpoint/resume is implemented for local runs with encrypted payloads, atomic per-run leases and workspace admission; these controls prevent concurrent resume through the application, but the SQLite database and key file are not an access-control boundary against a local user who can read the user's application-data directory. The optional MCP client has real SDK v2 stdio/Streamable HTTP lifecycle tests, exact tool grants, bounded calls and fail-closed manifest verification. A timed-out or transport-interrupted tool call is reported as unknown outcome and is never automatically replayed; reconnection only enables subsequent calls. A cross-platform supervisor adds a second kill-on-close Job Object on Windows or a dedicated process group on POSIX in ordinary Python runs; frozen packaged builds use the SDK cleanup unless a supervisor executable is bundled. The client still does not sandbox child servers or authenticate protected remote servers. Do not enable untrusted MCP packages or protected remote servers.
- Workforce children share one workspace and can observe sibling artifacts. A write-capable child can modify files within that workspace subject to the tool approval policy. Ready read-only tasks may run in parallel (`max_parallel`); a write-capable task always runs alone. Each child holds a resource-scheduler lease, so concurrent model loads queue for memory and idle models are unloaded rather than over-committing the GPU. There is no per-child OS isolation or distributed lease. The verifier is a model and can be wrong; human review remains required for consequential artifacts.
- The SQLite workforce/run event journals are hash-chained for tamper evidence but are not encrypted at rest. The checkpoint key is stored separately from the database, but both live under the user's application-data directory by default. Protect that directory and use the key-file environment override for a stronger secret-management arrangement.
- Prompt injection is not solved by system prompts. Every adapter, file path and external tool needs host-side policy.
- Remote Ollama endpoints receive prompts and local project context. Configure a remote endpoint only when its data-handling posture is acceptable.

## Production requirements before broader computer control

1. Done on Windows for executed commands (AppContainer + Job Object). Still required: the same boundary for MCP servers, and a disposable VM for tasks that need broader system access.
2. Separate read, write, delete, execute, network, GUI and credential grants.
3. Add tool-specific risk classes and policy evaluation; require approval for destructive writes, installs, external transactions, Git pushes and application control.
4. Store secrets outside model context; provide short-lived, scoped credential handles only when necessary.
5. Add sanitized observations and an explicit untrusted-data boundary for files, memory and web content.
6. Record append-only audit events for run start, model digest, tool request, policy decision, approval, execution, result and verification.
7. Add in-flight cancellation, process-tree cleanup, CPU/RAM/disk/process-count quotas and cleanup after application crashes.
8. Durable checkpoints bind model/harness/policy/tool manifest and refuse interrupted tools. Workforce children inherit the host tool policy and records; add per-child OS isolation and resource quotas before broader computer control.
9. Add SBOM, dependency/license scanning, vulnerability review, signed installers and reproducible Windows packaging.
10. Threat-model MCP server provenance, remote transport authentication, server capabilities and child-agent permission inheritance. The current client uses explicit per-server tool-name grants and environment-variable references for stdio secrets. OAuth, custom HTTP authorization headers, resource/prompt subscriptions and an MCP server are not implemented. The real transport suite covers stdio/HTTP initialization, invocation, timeout, cancellation, crash detection, reconnection, schema-drift refusal and process/session cleanup, but those checks are not a substitute for server sandboxing or remote authorization.

## Reporting vulnerabilities

Do not publish exploitable vulnerabilities in public issues. Contact the maintainers through a private security advisory on the GitHub repository.
